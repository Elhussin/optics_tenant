ممتاز، الآن نبدأ في أهم وثيقة بعد الدستور.

في رأيي **Enterprise Constitution** يجيب على سؤال **"لماذا؟"**، أما الوثيقة التالية فتجيب على سؤال **"كيف؟"**.

وهذه الوثيقة ستكون أكثر وثيقة سيستخدمها أنت وأي وكيل AI أثناء التطوير.

---

# Engineering Playbook v1.0

> **الهدف:** توحيد طريقة التطوير بحيث لا تعتمد على الشخص الذي يكتب الكود، وإنما على قواعد ثابتة قابلة للتكرار.

---

# الفصل الأول: دورة حياة أي ميزة (Feature Lifecycle)

**لا يجوز بدء كتابة الكود مباشرة.**

كل ميزة تمر بالمراحل التالية:

```text
Business Requirement
        │
        ▼
Business Analysis
        │
        ▼
Architecture Review
        │
        ▼
Impact Analysis
        │
        ▼
Implementation Plan
        │
        ▼
Backend
        │
        ▼
Frontend
        │
        ▼
Tests
        │
        ▼
Documentation
        │
        ▼
Review
        │
        ▼
Merge
```

إذا لم تمر الميزة بهذه المراحل، فهي تعتبر **غير مكتملة** حتى لو كانت تعمل.

---

# الفصل الثاني: قاعدة الـ Domain أولًا

أي تطوير جديد يجب أن يبدأ بالإجابة على سؤال واحد:

> **إلى أي Domain تنتمي هذه الميزة؟**

أمثلة:

| الميزة          | الـ Domain   |
| --------------- | ------------ |
| إطار نظارة جديد | Catalog      |
| كمية المخزون    | Inventory    |
| فاتورة بيع      | Sales        |
| قيد محاسبي      | Accounting   |
| وصفة طبية       | Prescription |
| ملف المريض      | Patient      |
| رصيد العميل     | Customer     |

إذا لم يكن هناك Domain واضح، فلا يبدأ التطوير حتى يتم تحديده.

---

# الفصل الثالث: قاعدة ملكية البيانات (Data Ownership)

كل كيان له **مالك واحد فقط**.

مثال:

* Product → Catalog
* Stock → Inventory
* Invoice → Sales
* Journal Entry → Accounting
* Patient → Patient Domain
* Employee → HR

أي Domain آخر يقرأ البيانات عبر API أو Services، ولا يعدلها مباشرة.

---

# الفصل الرابع: ممنوعات التطوير (Forbidden Patterns)

يمنع منعًا باتًا:

* كتابة Business Logic داخل `views.py`.
* كتابة Business Logic داخل `serializers.py`.
* كتابة SQL داخل React.
* استدعاء Domain آخر مباشرة.
* إنشاء جدول جديد دون مراجعة Canonical Data Model.
* نسخ الكود بدلًا من إعادة استخدامه.
* إنشاء API بلا توثيق.
* إنشاء Migration غير مراجعة.
* إضافة صلاحية دون تحديث Permission Matrix.

---

# الفصل الخامس: قواعد بناء Backend

كل Django App يجب أن يحتوي على هيكل ثابت:

```text
app/
│
├── models/
├── services/
├── repositories/
├── selectors/
├── api/
│   ├── serializers/
│   ├── views/
│   ├── permissions/
│   └── urls.py
├── filters/
├── tasks/
├── events/
├── signals/
├── tests/
└── admin/
```

**ملاحظة:** لن نفرض هذا الهيكل إذا كان يزيد التعقيد في تطبيق صغير داخل المشروع. الهدف هو وجود مكان واضح لكل مسؤولية، وليس إنشاء مجلدات فارغة.

---

# الفصل السادس: قواعد بناء Frontend

كل Feature في Next.js تكون مستقلة:

```text
features/
    inventory/
        api/
        components/
        hooks/
        forms/
        pages/
        types/
        utils/
```

ولا يجوز أن يعتمد Feature على ملفات Feature آخر إلا من خلال واجهات (Public API) واضحة.

---

# الفصل السابع: قواعد API

أي Endpoint يجب أن يحقق:

* اسم واضح.
* RESTful.
* Versioned عند الحاجة.
* Validation.
* Authorization.
* Pagination عند القوائم.
* Filtering.
* Sorting.
* OpenAPI Documentation.

ولا يُنشأ Endpoint إلا إذا عُرف الغرض منه والمستهلك (Frontend / Mobile / Integration).

---

# الفصل الثامن: قواعد قاعدة البيانات

قبل إنشاء أي جدول جديد يجب الإجابة عن:

1. هل يوجد جدول يؤدي نفس الغرض؟
2. من يملك هذا الجدول؟
3. هل يدعم Multi-Tenant؟
4. هل يحتاج Audit؟
5. هل يحتاج Soft Delete؟
6. ما هي الفهارس (Indexes) المطلوبة؟
7. ما تأثيره على الأداء؟

---

# الفصل التاسع: قواعد الأحداث (Events)

أي حدث تجاري مهم يجب أن يُمثل كحدث (Business Event)، مثل:

* SalesInvoiceCreated
* PurchaseOrderApproved
* StockTransferCompleted
* CustomerRegistered

ولا تُستخدم الأحداث لكل عملية صغيرة حتى لا يصبح النظام معقدًا بلا داعٍ.

---

# الفصل العاشر: قواعد المراجعة (Code Review)

لا يُدمج أي تغيير قبل التأكد من:

* يحقق متطلبات العمل.
* لا يكسر Multi-Tenant.
* لا يكسر API.
* لا يكرر الكود.
* مغطى بالاختبارات المناسبة.
* حدثت الوثائق إن لزم.
* لا يضيف دينًا تقنيًا غير مبرر.

---

# الفصل الحادي عشر: AI Development Protocol

أي وكيل AI يجب أن يمر بهذه القائمة قبل كتابة الكود:

1. قراءة Enterprise Constitution.
2. تحديد الـ Domain.
3. مراجعة الـ ADR المرتبط.
4. تحليل أثر التغيير.
5. اقتراح خطة تنفيذ.
6. تنفيذ أقل تغيير ممكن (Smallest Safe Change).
7. كتابة أو تحديث الاختبارات.
8. تحديث الوثائق إذا تغير السلوك أو التصميم.

---

# الفصل الثاني عشر: Definition of Done

لا تعتبر المهمة منتهية إلا إذا:

* تم تنفيذ الوظيفة المطلوبة.
* مرت الاختبارات.
* لم تكسر أي وحدة أخرى.
* تم تحديث التوثيق إذا لزم.
* راعى التغيير الأداء والأمان.
* يمكن لمطور آخر فهم التغيير بسهولة.

---

# قرار معماري جديد (ADR-000)

أود أن أضيف أول قرار معماري رسمي، لأنه سيؤثر على المشروع كله.

## **ADR-000: Evolution Before Rewrite**

**القرار:**

> **المشروع لن يُعاد بناؤه من الصفر إلا إذا أثبتت الأدلة التقنية أن إعادة الهيكلة التدريجية غير ممكنة.**

**السبب:**

* المشروع يحتوي بالفعل على جهد كبير.
* توجد وحدات مستقرة يمكن البناء عليها.
* إعادة الكتابة الكاملة تحمل مخاطر فقدان المعرفة وتأخير الوصول للإنتاج.

**النتيجة:**

* الأولوية دائمًا لإعادة الهيكلة (Refactoring).
* إعادة البناء تقتصر على الوحدات التي لا يمكن إنقاذها.
* أي اقتراح بإعادة كتابة وحدة كاملة يجب أن يتضمن تحليلًا واضحًا للمخاطر والفوائد وخطة انتقال.

---

## الخطوة التالية التي أعتبرها الأكثر أهمية

أعتقد أن الوقت مناسب للبدء في **Business Architecture**، وليس في الكود.

لكنني لا أقصد رسم مخطط عام، بل بناء **Domain Map** احترافي يحدد حدود كل وحدة في النظام.

هذه الوثيقة ستكون الأساس الذي سيمنع تداخل المسؤوليات بين المبيعات، والمخزون، والمحاسبة، وملف المريض، وغيرها. وهي، في رأيي، أهم وثيقة هندسية بعد الدستور مباشرة، لأنها ستحدد "من يملك ماذا" داخل النظام، وستكون المرجع الذي يُبنى عليه كل تطوير لاحق.
