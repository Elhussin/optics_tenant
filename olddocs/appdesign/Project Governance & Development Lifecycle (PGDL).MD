**الحالة: معتمد للمشروع**

## 1. فلسفة وأهداف الحوكمة (Governance Philosophy)

الهدف من هذه الوثيقة هو إرساء قواعد عمل صارمة وملزمة لجميع المطورين ووكلاء الذكاء الاصطناعي (AI Agents) لمنع العشوائية والتعارض التقني، وضمان الحفاظ على هوية ومعمارية النظام المحددة في **Enterprise Constitution** و**Engineering Playbook**.

### الأهداف الرئيسية:
* **منع التعارض والتضارب:** توحيد آلية التعديل على قاعدة البيانات، الـ APIs، والـ Domains المشتركة.
* **منع تسريب البيانات بين المستأجرين (Tenant Leakage):** إجبار كل استعلام أو تعديل على اتباع ضوابط العزل.
* **الالتزام بـ Domain Ownership:** منع أي تطبيق من العبث ببيانات تطبيق آخر دون المرور بالواجهات الرسمية (APIs/Services/Events).
* **إدارة التغيير المتوازي:** تمكين عدة مطورين ووكلاء AI من العمل على نفس المشروع بالتوازي دون إحداث تعارضات في الـ Git أو الـ Migrations.

## 2. دورة حياة الميزة وقبول الكود (Feature Development Lifecycle)

لا يجوز البدء في كتابة أي سطر كود قبل المرور بمراحل التصميم والتحليل التالية. أي كود يخالف هذه الدورة يُرفض دمجُه تلقائيًا:

```text
Requirement ──> Domain Assignment ──> Impact Analysis ──> Plan Approval ──> Code ──> Verify ──> DoD Check
```

### الخطوة الأولى: تحديد الـ Domain والمالك (Domain Assignment)
* يتم تصنيف الميزة المطلوبة وربطها بـ Domain محدد من الـ 20 Domain المذكورة في [Business Domain Architecture](file:///c:/code/optics_tenant/appdesign/Business%20Domain%20Architecture%20%28BDA%29.md).
* لا يسمح بخلط المسؤوليات (مثل وضع منطق التأمين الطبي داخل المبيعات).

### الخطوة الثانية: تحليل الأثر (Impact Analysis)
* فحص أثر التغيير على [Canonical Data Model](file:///c:/code/optics_tenant/appdesign/Canonical%20Data%20Mode.md) والتأكد من عدم تكرار الجداول أو الحقول.
* فحص العلاقات بين الـ Domains وتأكيدها في الـ **Bounded Context Map**.
* تحديد ما إذا كان التغيير سينتج عنه أحداث (Events) جديدة وتوثيقها في **Event Catalog**.

### الخطوة الثالثة: خطة التنفيذ المعتمدة (Implementation Plan)
* كتابة خطة تنفيذ واضحة تحدد الملفات المراد تعديلها أو إنشاؤها.
* بالنسبة لوكلاء الذكاء الاصطناعي، **يجب الحصول على موافقة المستخدم الصريحة** على الخطة قبل إجراء أي تعديل.

### الخطوة الرابعة: التطوير (Coding Rules)
* تطبيق منطق الأعمال في طبقة الـ **Services** حصريًا، ويُمنع نهائيًا كتابة أي Business Logic في الـ Views أو الـ Serializers أو الـ React Components.
* اتباع هيكل المجلدات الموحد للـ Backend والـ Frontend الموضح في الـ Playbook.

### الخطوة الخامسة: التحقق والاختبار (Verification & Testing)
* كتابة اختبارات وحدة (Unit Tests) للـ Services الجديدة.
* كتابة اختبارات تكاملية (Integration Tests) للـ APIs المضافة.
* فحص توافق الـ API مع مواصفات OpenAPI.

## 3. ضوابط العمل المشترك ومنع التضارب (Collaboration & Conflict Prevention)

لتسهيل العمل المتوازي ومنع تعارضات الكود، نلتزم بالقواعد التالية:

### أ. إدارة الفروع (Branching Strategy)
* تُسمى الفروع بالشكل التالي:
  * للميزات الجديدة: `feature/<domain-name>/<feature-name>` (مثال: `feature/sales/zatca-ubl-invoice`)
  * لإصلاح الأخطاء: `bugfix/<domain-name>/<issue-description>`
  * للمهام العاجلة: `hotfix/<domain-name>/<issue-description>`
* يمنع المطورون والوكلاء من العمل مباشرة على الفروع الرئيسية (`main` أو `master` أو `develop`).

### ب. تكامل وإدارة قواعد البيانات والـ Migrations
* **قاعدة الميجريشنز (Migrations):** لا يتم تعديل الجداول أو الحقول يدويًا في قاعدة البيانات. كل تعديل يجب أن يمر عبر Django Migrations.
* **منع تعارض الـ Migrations:** في حال العمل المتوازي، يجب التأكد من عدم تداخل أرقام الميجريشنز. إذا حدث تعارض، يتم دمج الفروع وتوليد ميجريشن دمج (`merge migration`) باستخدام أمر Django الرسمي:
  `python manage.py makemigrations --merge`
* **عزل المستأجرين (Tenant Isolation):** أي Migration يخص جداول المستأجرين يجب أن يتم تصنيفه ليعمل ضمن مخطط المستأجر (`tenant apps`) وليس العام (`public apps`).

### ج. أمن وحماية الأسرار (Secrets & Credentials Security)
* **يُمنع منعًا باتًا** كتابة كلمات المرور، مفاتيح الـ API، أو المفاتيح السرية (`SECRET_KEY`) داخل الكود أو في ملفات `.env` المرفوعة للمستودع.
* يجب استخدام ملف `.env.template` كدليل للمتغيرات البيئية المطلوبة.
* يتم تمرير الأسرار الحقيقية عبر البيئة الحاضنة (Environment Variables) أو عبر نظام إدارة الأسرار (Secrets Manager).

### د. تكامل الاعتمادات (Dependency Integrity)
* للـ Backend: يُستخدم **PDM** حصريًا لإضافة أو تحديث أي مكتبات عبر ملف `pyproject.toml` والالتزام بـ `pdm.lock`.
* للـ Frontend: يُستخدم **npm** حصريًا والالتزام بـ `package-lock.json`.
* يمنع تثبيت أي مكتبة بشكل عشوائي دون تسجيلها في ملفات إدارة الحزم الرسمية.

## 4. معايير جاهزية الميزة للدمج (Definition of Done - DoD)

لا تُعتبر أي مهمة منتهية ويُحظر دمجها إلا إذا استوفت المعايير التالية:

1. **تحقيق المتطلبات بالكامل:** أن تكون الميزة تعمل وتقدم القيمة التجارية المطلوبة دون أي وظائف ناقصة.
2. **الالتزام بالمعمارية (Clean Architecture):** عدم وجود تسريب للمنطق البرمجي إلى طبقات العرض والواجهة.
3. **الاختبارات الآلية:** مرور جميع الاختبارات بنسبة نجاح 100% وكتابة اختبارات تغطي الكود الجديد.
4. **التوافق التراجعي (Backward Compatibility):** عدم تسبب التعديل في كسر أي API مستخدم من قبل تطبيق الهاتف المحمول أو شاشات الواجهة الأخرى.
5. **خلو الكود من الديون التقنية غير المبررة:** مراجعة جودة الكود وتجنب التكرار (DRY) والأشياء الصلبة (Hardcoded values).
6. **التوثيق وتحديث المعمارية:** تحديث وثائق الـ appdesign المرتبطة (مثل إضافة الأحداث الجديدة إلى Event Catalog أو الـ APIs الجديدة إلى API Catalog).

## 5. ميثاق عمل وكلاء الذكاء الاصطناعي (AI Agent Protocol)

بما أن وكلاء الذكاء الاصطناعي يمتلكون صلاحية كتابة وتعديل الكود مباشرة، يجب عليهم الامتثال للميثاق التالي:
1. **القراءة الإلزامية:** قراءة ملفات المعمارية الستة والتأكد من فهم حدود الـ Domains والـ Workflows ذات الصلة بالمهمة.
2. **منع التعديل المفاجئ والممتد:** يُمنع تعديل ملفات متعددة بشكل واسع دون مبرر. يجب اقتراح أقل تعديل آمن ممكن لحل المشكلة (Smallest Safe Change).
3. **التدقيق المزدوج للميجريشنز وسكريبتات التخريب:** التحقق من أي كود يحتوي على حذف بيانات أو تعديل جذري لهياكل الجداول والحصول على موافقة صريحة ثانية.
4. **تأكيد عزل الـ Tenant:** التحقق من عدم وجود أي استعلام عام لقاعدة البيانات مثل `objects.all()` دون تطبيق تصفية المستأجر والفرع والصلاحية المناسبة.
